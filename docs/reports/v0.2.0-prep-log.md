## R1 Docker での起動（2026-11-25）

### 実測

- main `20312e1` で `docker build -t anlage-v020-check .` は失敗した（exit 5）:
  ```
  An error occurred while installing fiddle (1.1.8), and Bundler cannot continue.
  openehr-rails was resolved to 0.9.0, which depends on
    openehr was resolved to 2.5.0, which depends on
      locale was resolved to 2.1.5, which depends on
        fiddle
  extconf failed, exit code 1
  ```
- 原因: ビルドの段（`FROM base AS build`）に libffi のヘッダが無い。`libffi-dev` を足すとビルドが通った（Docker 29.9.1）
- 起動: `docker run -e SECRET_KEY_BASE=… -p 3999:80` で、`/up`・`/templates`・`/patients` が 200（`config/master.key` 無し）。
  `bin/docker-entrypoint` が `db:prepare` を流すので、空の volume でも起動する
- README に書いた手順（`docker build` → `docker run … -v <volume>:/rails/storage` → `curl /up`）を、名前だけ変えてそのまま流し、200 を確認した。
  確認に使ったイメージと volume は消した

### 判断（自己承認、Issue #142 の範囲内）

- Dockerfile はビルドの段に `libffi-dev` を足すだけ（実行の段は `libvips` の依存で libffi が入るため、起動で落ちないことを実測で確認）
- TLS の設定（`assume_ssl`・`force_ssl`）は変えない。既知の制限に書いた（外に出すなら TLS を終端するプロキシの後ろ）
- `docker-compose.yml` は足さない（単一のコンテナで足りる。足すかは公開のあとの Issue に）

## R4（2026-11-26）患者を選ばないと保存できない（`skoba/anlage#161`。R-20261126-2 の 5）

- 規則:
  - 新しい記録の保存（`POST /compositions/:template_id`）は、いまの患者（`session[:ehr_id]`）が無ければ 422。帳票のエラーは「患者を選んでいません。患者を選んでから保存してください」。
  - 帳票の画面は、注記「患者を選んでいません。保存するには、先に患者を選んでください。」（「患者」は一覧へのリンク）を出し、保存のボタンを出さない。
  - 修正（PATCH）は元の EHR のままで、いまの選択に依らない。
- 判断（自己承認）:
  - 検査の順は「閲覧専用 → 患者 → 値の検査」にした。患者を選んでいなければ、値を直しても保存できないので、先に知らせる。
  - 帳票の画面は、項目は見せて保存のボタンだけを隠す。帳票の中身を確かめる用途（取り込みのあと）を残す。
- Red（`spec/requests/patient_required_spec.rb`）:
  - 注記が無い（`undefined method 'text' for nil`）。
  - 選ばずに POST すると記録が増える（`did change from [0, 0] to [1, 1]`）。
- Green のあと、全 suite で 43 件が赤。どれも患者を選ばずに保存していた spec（19 ファイル。うち system spec 7）。
  - 記録を保存する spec の前提に、いまの患者を選ぶ手順を足した（`spec/support/patient_selection.rb` の `select_patient`、`select_patient_in_browser`）。
  - デモクエリ 5 の「壇上で 1 件足す」は、`demo:reset` のあとで `DEMO-01` を選んでから保存する（台本の操作列と同じ）。
  - `records_to_ehr_spec.rb` の「選んでいなければ EHR に結び付けない」は、「選んでいなければ保存しない」に書き換えた。
    患者の画面に未割り当ての記録が出ないことの確かめは、committer で直接入れた記録で行う（#161 より前の記録の代わり）。
  - 患者を選ぶと、ナビの下に「選択を外す」（DELETE のフォーム）が出る。そのため、画面の DELETE のフォームや送信ボタンを数える 3 か所の選択子を、記録のフォーム（`form[action^='/compositions']`）に絞った。
- 既知の制限の 3 は「解消」と書き、番号は残した（裁定が 13・18 を番号で指すため）。開発機の、患者に結び付かない記録には触らない。

## R7（2026-11-26）Docker で初期データを入れる（`skoba/anlage#168`。受け入れの台本の前提）

- 台本の「Docker での起動 → 初期データの投入」が、そのままでは通らない。
  - `rake demo:reset` は production では止まる（`lib/tasks/demo.rake` の `abort`）。Docker のイメージは production。
  - イメージには `spec/fixtures/`（OPT と紹介状の骨格）が入っている（`.dockerignore` は `spec/` を除かない。`COPY . .`）。
- 判断（自己承認）:
  - 採った案: `ANLAGE_ALLOW_DEMO_RESET=1` を与えたときだけ、production でも動かす。全データを消す操作なので、値は `1` だけを許す。
  - 捨てた案:
    - production の止めを外す（誤って消す）。
    - `rails runner` で手順を写す（同じ手順が 2 か所になる）。
- Red: production を装い、`ANLAGE_ALLOW_DEMO_RESET=1` で invoke する例。`abort` の SystemExit が例の外に抜け、rspec の実行がそこで終わった（`7 examples, 0 failures` で、足した 2 例のあとが走らない）。
- Green: `spec/tasks/demo_reset_spec.rb` 8 examples、0 failures。`1` 以外（`true`）では止まる。
- README の Docker の手順に `docker exec -e ANLAGE_ALLOW_DEMO_RESET=1 anlage bin/rails demo:reset` を書いた。
