## 1. 流れ

```
問い（日本語）
  │
  ├─ 1. パスカード検索（Opt::PathcardSearch。別名表を含む）で、候補のカードを取る
  │
  ├─ 2. LLM に、問いと候補のカードの文を渡す
  │      LLM が返すのは「選択」: どのカードを表示するか、どのカードにどの条件を付けるか、条件の値
  │
  ├─ 3. 選択を検査する（カードの番号が候補にあるか、演算子がカードの型に合うか、値が値集合にあるか）
  │
  ├─ 4. クエリビルダー（QueryBuilder::Builder）が、選択から AQL を組む
  │
  ├─ 5. リンタ（QueryBuilder::Linter）に通す。error が 1 つでもあれば、実行しない
  │
  ├─ 6. 実行する（OpenehrRails::Aql::Executor）
  │
  └─ 7. 説明を出す。何をどう引いたかを、カードの言葉（ラベル、容器の名前、値集合の表示名）で書く。
         説明は、選択とカードから決まった形で組む。LLM には書かせない
```

- 1・4・5・6 は、いまある部品をそのまま使う（実測: `Opt::PathcardSearch.call`、`QueryBuilder::Builder.build`、
  `QueryBuilder::Linter.lint`、`QueryBuilder::Runner.call` が main にある）
- 2 が失敗したとき（LLM が設定されていない、応答が読めない、検査 3 で落ちる、リンタで落ちる）は、
  **クエリビルダーの画面に落ちる**。候補のカードは 1 で取れているので、利用者は手で選んで続けられる
- 画面は、クエリビルダーの上に「問いを文で入れる」欄を 1 つ足す形にする。LLM が返した選択は、クエリビルダーの
  「表示する項目」「条件」にそのまま入る（URL の状態になる）。利用者は、実行の前に見て、直せる
- 説明の例（a002「診断確度が『疑い』の傷病名」のとき）:
  「**プロブレム・診断**の **プロブレム・診断名** を表示します。条件: **診断確度** が **疑い**（at0074）。
  アーキタイプ: openEHR-EHR-EVALUATION.problem_diagnosis.v1。テンプレート: ProblemList」

## 2. LLM の役割の境界（LLM 分業原理）

### 2.1 LLM が出してよいもの、出してはいけないもの

| | 出どころ |
|---|---|
| どのカードを使うか（対応付け） | **LLM**。ただし、渡した候補の中の番号で指す |
| 条件の値（数値、日付、文字列）の抽出 | **LLM**。問いの文から抜き出す |
| 演算子（以上、未満、いずれか、範囲、含む、未記入を含む、どちらか） | **LLM**。ただし、カードの型で使えるものだけ（`QueryBuilder::Builder::OPERATORS`） |
| パス、アーキタイプの ID、at-code | **カード**（`identity`）。LLM は書かない |
| 型、終端のホップ（magnitude、defining_code/code_string など） | **カード**（`semantics.rm_type`）とクエリビルダー |
| 値集合のコード | **カード**（`constraints.value.code_list`）。LLM は、渡した表示名の中から選び、コードはカードから引く |
| AQL の形（SELECT、FROM、CONTAINS、WHERE） | **クエリビルダー** |
| 説明の文 | **カードの文言**から、決まった形で組む |

### 2.2 推す案: LLM は「選択」を出し、AQL はクエリビルダーが組む（Q1）

裁定の流れは「LLM が AQL を作る」と書く。一方で、LLM が出してよいのは対応付けと値の抽出だけ、とも書く。
この 2 つを両方とも満たす形として、**LLM の出力を、クエリビルダーへの入力（選択）に限る**案を推す。

- 選択の形は、評価 v2 の `selection` と同じ（`docs/design/s1-eval-v2-plan.md` 8.1・8.4・8.5。カード、演算子、値、
  `include_missing`、`any`、`template_id`、`across_versions`）。いまの aql の 12 問は、この形から 12/12 で組めている（実測）
- LLM の出力に、パスも at-code もコードも現れない。LLM が間違えられるのは「カードの選び方」と「値」だけになり、
  間違いは検査 3 とリンタで見つかるか、説明の文で利用者に見える
- 出力は、決まった JSON の形に縛る（API の側の、出力の形を縛る機能を使う。3 節）

**ほかの案: LLM に AQL の文字列を書かせる**

- カードの文（パスを含む）を渡し、AQL を書かせて、リンタで検査する
- 長所: クエリビルダーが組めない形（2 つのアーキタイプの結合、並べ替え、集計）にも届きうる
- 短所: LLM がパスと at-code を書き写す。写し間違いはリンタが落とすが、「実在する別のパス」に書き換わった場合は落ちない。
  いまの AQL エンジンの方言（終端のホップ、`CONTAINS` の形）を指示文で教える必要があり、エンジンの版に指示文が縛られる
- この案は、**製品の経路には採らず、測定の腕の 1 つとして測る**（5 節の G-AQL）。「選択」の案より正答率が高ければ、考え直す材料になる

### 2.3 実行しない条件

- リンタの error が 1 つでもある AQL は実行しない（いまのクエリビルダーと同じ。`Lint#ok?`）
- LLM が返したカードの番号が候補に無い、演算子がカードの型に合わない、値集合に無い値、のどれかがあれば、組まない
- LLM が「この問いは、候補のカードでは答えられない」と返せるようにする（選択を空にして、理由を 1 文）。そのときは、クエリビルダーに落ちる
- LLM の出力を、そのまま SQL やシェルに渡す経路は作らない。AQL は読み出しだけ

## 3. アダプタ

### 3.1 形

アダプタは、**文を送って文を受け取るだけの汎用の部品**にする（R-20261127-14）。問い合わせ専用の形にしない。
カードも選択も知らない。ほかの入口（定義の案を出す入口など）が、あとで同じ部品を使える。今回、その入口は作らない。

```
Llm::Adapter（口）
  #complete(instructions:, input:) → Llm::Response（text、model、input_tokens、output_tokens）
  #name（測定の記録と画面に使う）、#external?（外に文を送るか）
  落ちるときは Llm::Error（通信の失敗、時間切れ、断り、記録が無い）

実装
  Llm::Adapters::Recorded   記録した応答を返す（spec と、測定の再現に使う。7 節）。外を呼ばない
  Llm::Adapters::Anthropic  API のモデル（段 4）
  Llm::Adapters::Local      手元で動くモデル（段 5）

まわり
  Llm::Settings   環境変数から、オンとオフ、アダプタ、回数の上限を読む（10 節）。オフのとき、アダプタは無い
  Llm::Usage      使った回数とトークンの数を数える（10 節）

問い合わせの側（アダプタの外）
  NlQuery::Prompt            指示文と、カードの文を組む
  NlQuery::SelectionParser   応答を選択に直して検査する
  NlQuery::Explanation       選択とカードから、説明の文を組む
  NlQuery::Runner            検索 → アダプタ → 選択、をつなぐ
```

- モデルを替えても、検査は同じものが通る
- 「LLM なし」は、アダプタの 1 つではなく、オフの状態として持つ（オフのとき、`NlQuery::Runner` は候補のカードだけを返す）

### 3.2 既定をどれにするか（Q2）

**推す案: 既定は「LLM なし」**。理由:

- Anlage は、置けば動く参照実装。鍵も、手元のモデルも無い状態で、クエリビルダーまでが動くのが既定であるべき
- 外に文を送る動きは、利用者が自分で設定したときだけにする（4 節）
- 「設定したときに、どのモデルを推すか」は、測定の結果（5 節）で決める。いまは決めない

### 3.3 測定に使う候補と、比べ方（Q3）

| 候補 | 種類 | 入力／出力の値段（100 万トークンあたり） | 見どころ |
|---|---|---|---|
| Claude Sonnet 5.5（`claude-sonnet-5-5`） | API | 2 ドル／10 ドル | 中位。ふだん使いの見込み |
| Claude Haiku 5.5（`claude-haiku-5-5`） | API | 0.10 ドル／0.50 ドル | 最も安い。これで足りるなら、費用はほぼ無視できる |
| Claude Opus 5.5（`claude-opus-5-5`） | API | 4 ドル／20 ドル | 上位。上の 2 つで足りないときにだけ足す |
| 手元のモデル 1 つ | 手元 | 0（電気代と時間） | 外に何も送らない。日本語と JSON の出力がどこまで保てるか |

- 値段とモデルの ID は、Claude Code に同梱の API の資料（2026-11-03 時点の写し）による。**実装の前に、公式の文書で確かめ直す**
  - **確かめ直した（2026-11-27）**: モデルの ID（`claude-sonnet-5-5`、`claude-haiku-5-5`、`claude-opus-5-5`）と、上の表の値段は、
    公式の文書（platform.claude.com の models/overview と pricing）と同じ。Haiku 5.5 は、入力が 10 万トークンを超える問い合わせでは
    0.50 ドル／2.50 ドルになる（この用途では超えない）。考える分のトークンが出力として数えられるかは、その 2 つのページには書かれていなかった（未確認）
- 手元のモデルの候補（どのモデルを、どの道具で動かすか）は、**まだ調べていない**。承認のあと、開発機で動く大きさのものを
  2〜3 選び、日本語の問いと JSON の出力で試してから 1 つに絞る。手元で動かす道具を入れるのは開発機の設定の変更なので、そこでゲート報告にする
- 比べ方: 5 節の測定を、同じ問い・同じ指示文・同じカードの文で、モデルだけを替えて回す。見るのは、
  正答率（行の一致）、リンタを通った率、JSON として読めた率、1 問あたりの時間、1 問あたりの費用

### 3.4 API の側で確かめてあること（資料による。実装の前に確かめ直す）

- Ruby の公式の SDK は gem `anthropic`。`Anthropic::Client.new` は、環境変数 `ANTHROPIC_API_KEY` を読む
- 出力を JSON の形に縛る機能がある（`output_config` の `format`）。Ruby での書き方は、資料の該当の節をまだ読んでいない
- 新しいモデルは、`temperature` などを受け付けない（送ると 400）。**同じ問いでも、応答は毎回同じとは限らない**。
  くり返して測る理由（5 節）
- 新しいモデルは、応答が「断り」（`stop_reason` が refusal）で終わることがある。そのときは「答えられない」として扱う

## 4. 外に送るもの

### 4.1 送るもの、送らないもの

| | API のアダプタ | 手元のアダプタ |
|---|---|---|
| 利用者の問い | 送る | 手元の中だけ |
| 候補のカードの文（下の形） | 送る | 手元の中だけ |
| 決まった指示文 | 送る | 手元の中だけ |
| 記録の中身（実行の結果、患者の ID、氏名） | **送らない** | 送らない |
| テンプレート（OPT）のファイル | 送らない | 送らない |
| 用語マスターの中身 | **送らない** | 送らない |

- 説明の文を LLM に書かせないのは、このため。実行の結果を LLM に渡さなければ、記録の中身は外に出ない
- 扱うのは、サンプルデータだけ（`rake demo:reset` の初期データ。架空の患者）。ただし、利用者が問いの文に何を書くかは止められない。
  画面に「問いの文は、外の API に送られます。患者の情報を書かないでください」と出す（文言は語彙表で決める）

### 4.2 カードの文の形

1 枚を 1 行にする。送る項目は、次だけ。

```
<番号> | <ラベル> | <容器の名前> | <型> | <値集合の表示名（あれば）> | <単位（あれば）> | <テンプレート>
```

- 実測: 初期データの 18 枚を、アーキタイプの ID と at-code も入れた形で並べて 1,702 文字。全部を送っても小さい
- 番号は、その問い合わせの中だけの連番。LLM は番号で指し、アプリが番号からカードに戻す
- **送らない項目**: パス、at-code、説明（英語の原文が多い。16/18 枚）、`bindings`（下）、出どころの情報（`provenance`）
- G-AQL の腕（5 節）だけは、パスとアーキタイプの ID も送る（AQL を書かせるため）

### 4.3 コンテンツ防火壁を、どう守るか

- カードの文言の出どころは、テンプレート（OPT）の用語。CKM の公開アーキタイプ由来で、ライセンスのある用語マスターではない
- カードは `bindings`（外の用語へのコードの結び付け）を持つ。実測: 18 枚のうち 9 枚にあり、中身は SNOMED CT のコード
  （例 `[SNOMED-CT(2003)::271649006]`）。**`bindings` は送らない**。送る項目を上の一覧に限ることで守る（許可した項目だけを送る作り）
- 外の値集合（`code_list` が空で、用語マスターから引くもの）は、いまのカードには展開していない。将来、用語マスター
  （ICD-11、MEDIS など）の表示名をカードや値の候補に載せる段が来ても、**その表示名は送らない**。送ってよい出どころを
  「テンプレート由来の文言」に限り、出どころが用語マスターの文言には印を付けて、文を組むところで落とす
- いまのカードのスキーマ（1.2）には、「用語マスター由来」の印の項目が無い（実測）。印を足すのはスキーマの変更なので、ここではしない。
  代わりに、**値集合の表示名は、コードが at-code（アーキタイプの中の用語）のものだけを送る**。実測: いまの 4 つの golden
  （`spec/fixtures/pathcards/*.golden.json`）で、`code_list` のコードはすべて at-code。外の用語のコードが `code_list` に入るようになっても、
  その表示名は文に入らない
- spec で固定する: 文を組む部品に、`bindings` を持つカードと、at-code でないコードの値集合を渡して、出力に現れないこと（7 節）
- 埋め込み（ベクトル化）は、この計画に入らない（S3 の段 E は保留のまま）

## 5. 測定: 接地あり・なし

### 5.1 比べるもの（腕）

同じ問いを、次の 3 つの腕に通し、返ってきた AQL を同じ採点器（`Evaluation::AqlScorer`）で採点する。

| 腕 | LLM に渡すもの | LLM が返すもの | AQL を組むのは |
|---|---|---|---|
| **N（接地なし）** | 問い、AQL の方言の説明、初期データにあるアーキタイプの ID の一覧 | AQL の文字列 | LLM |
| **G-AQL（接地あり、AQL を書く）** | N と同じもの ＋ 候補のカードの文（パスつき） | AQL の文字列 | LLM |
| **G-選択（接地あり、選択を出す）** | 問い、候補のカードの文（パスなし） | 選択（JSON） | クエリビルダー |

- N と G-AQL の違いは、カードの文があるかどうかだけ。これが「接地あり・なし」の比較
- G-AQL と G-選択の違いは、LLM の役割の広さ。これが Q1 の判断の材料
- 方言の説明（終端のホップ、`CONTAINS` の形、使える演算子）は、N と G-AQL に同じ文を渡す。
  渡さないと、N の誤りの多くが「エンジンの方言を知らない」になり、接地の効果と混ざる
- N に、アーキタイプの ID の一覧を渡すかどうかは、2 通りを測る（N0: 渡さない、N1: 渡す）。N0 は「何も知らない LLM」、
  N1 は「どのアーキタイプがあるかだけ知っている LLM」。主に比べるのは N1 と G-AQL
- どの腕も、返ってきた AQL はリンタに通してから実行する。リンタで落ちたものは「不正解（リンタで落ちた）」に数え、実行しない

### 5.2 問い（Q4・Q5）

- いまの aql の問いは 12 問（実測: 参照 AQL もクエリビルダーの経路も 12/12）。**12 問では、1 問で 8 ポイント動く**
- 足し方の案: いまの 12 問のそれぞれに、言い方を変えた文を 1〜2 つ足す（「血圧の上が 140 以上」「高血圧の疑いのある人」など、
  臨床の現場の言い方）。期待行は元の問いと同じなので、足すのは文だけ。30 問ほどにする
- **いまの文は、出す列を書いていない問いがある**（例: a001「収縮期血圧が 140 mmHg 以上の記録」の期待行は、収縮期の値の 1 列）。
  行の一致で採点すると、LLM が拡張期も出しただけで不正解になる。測定用の文（`nl_query`）を別に持ち、出す列まで書く
  （「…の記録の、収縮期の値」）。元の `query` は変えない
- 文の案はセッションが出し、レビューは人間（評価のゴールドは人間の専有領域）。**人間の時間が要るのは、ここ**
- 版をまたぐ問い（a014）は、G-選択では `across_versions` で扱える。N と G-AQL では、版ごとの AQL を 2 本書かせる形になるので、
  3 つの腕の比較からは外し、G-選択だけで別に数える

### 5.3 採点

| 指標 | 意味 |
|---|---|
| 行の一致（主） | 返ってきた行が、期待行と多重集合として一致した（`AqlScorer` の `:match`） |
| リンタを通った | リンタの error が無かった |
| 実行できた | 実行して、エラーにならなかった |
| カードの一致 | 使ったカード（アーキタイプと at-code）が、問いの `cards` と一致した（どこで間違えたかを見る） |
| 読めた | 応答が、決まった形（AQL の 1 文、または選択の JSON）として読めた |

- 不正解は、どこで落ちたかで分ける: 読めない／リンタで落ちた／実行できない／行が違う（カードが違う、値が違う、列が違う）

### 5.4 くり返しと、ばらつきの扱い

- 1 つの問い・1 つの腕・1 つのモデルにつき、**5 回**くり返す（応答は毎回同じとは限らない。3.4）
- 問いごとに「5 回のうち何回正解したか」を出す。全体は、次の 3 つを並べて書く
  - 平均の正答率（全部の試行のうち、正解した割合）
  - いつも正解した問いの数（5/5）、いつも不正解の問いの数（0/5）、ゆれた問いの数（1/5〜4/5）
  - 5 回それぞれの正答率の、最小と最大
- 腕の比較は、**同じ問いどうしで**比べる（問いごとに、G の正解数 − N の正解数）。問いをまたいだ平均だけで言わない
- 30 問では、数ポイントの差は言えない。「N はほとんど通らず、G はほとんど通る」のような大きな差だけを結果として書き、
  小さな差は「この問いの数では分からない」と書く。検定の値は、参考として付けるにとどめる
- 手元のモデルで乱数の種を固定できるなら、固定した 1 回と、固定しない 5 回の両方を測る

### 5.5 記録するもの（1 回の測定ごと）

測定の結果は、1 回ごとに 1 つのディレクトリに残す（置き場所の案: `docs/reports/s4-runs/<日付>-<名前>/`）。

- モデルの ID（API に送った文字列そのまま）と、応答に入っているモデルの名前。アダプタの名前
- 送った設定（出力の上限、考える深さの設定など。送らなかった設定は「既定」と書く）
- 指示文とカードの文の、sha256。指示文そのものも、リポジトリに置く
- anlage の commit の SHA、openehr と openehr-rails の版、テンプレートごとの `source_checksum`（カードの出どころ）
- 問いの一覧のファイルの sha256、くり返しの回数、日時
- 試行ごとの、送った文、返ってきた文、採点の結果、かかった時間、使ったトークンの数
- API のモデルは、同じ ID でも中身が変わりうる。**日付とモデルの ID を必ず並べて書き**、あとで測り直したときに数字が違っても、
  どちらも残す

### 5.6 先に決めておくこと

- 測る前に、腕、問い、くり返しの回数、主の指標（行の一致）を、この計画書と測定の設定のファイルに書いて commit する。
  結果を見てから、指標や問いを替えない。替えるときは、替えた理由と、替える前の結果を残す
- 指示文は、測定用の問いを見ながら調整しない。調整用に、測定に使わない問いを数問だけ別に持つ

## 6. 足す gem、鍵の持ち方、費用の見込み

### 6.1 gem

| gem | 何に使う | いつ |
|---|---|---|
| `anthropic`（公式の Ruby の SDK） | API のアダプタ | 承認のあと。`Gemfile` を変える PR は、人間がマージする |

### 6.2 鍵の持ち方

- 鍵は、環境変数で渡す（`ANTHROPIC_API_KEY`。SDK が読む）。リポジトリにも、Rails の credentials にも入れない
- `.gitignore` は、すでに `/.env*` と `/config/*.key` を外している（実測）
- 鍵が無いとき、API のアダプタは「設定されていない」と返し、クエリビルダーに落ちる。例外で画面を落とさない
- CI は、鍵を持たない。CI で動くのは、記録した応答のアダプタだけ。**CI から外の API を呼ばない**
- 測定は、開発機で、人間が鍵を渡したときだけ回す。記録（5.5）に、鍵やヘッダが入らないことを spec で固定する
- Docker の例（README）には、鍵を渡す環境変数の名前だけを書く

### 6.3 費用の見込み（見込み。トークンの数は、まだ測っていない）

- 1 回の問い合わせ: 入力は、指示文とカードの文と問いで 3,000 トークンほど、出力は、考える分を含めて 2,000 トークンほど、と置く
- 測定 1 回: 30 問 × 腕 4 つ（N0、N1、G-AQL、G-選択）× 5 回 = 600 回

| モデル | 1 回あたり | 測定 1 回（600 回） |
|---|---|---|
| Claude Haiku 5.5 | 0.0013 ドル | 0.8 ドル |
| Claude Sonnet 5.5 | 0.026 ドル | 16 ドル |
| Claude Opus 5.5（足すなら） | 0.052 ドル | 31 ドル |

- Sonnet と Haiku で測って、17 ドルほどの見込み。指示文の調整と、やり直しを見て、**上限を 50 ドルに置く**（Q7）
- 承認のあと、最初に、トークンを数える口（API にある）で実際の数を測り、この表を書き直す。大きく外れたら、回す前に報告する
- 画面での利用（測定の外）は、利用者が自分の鍵で払う。1 回の問い合わせの値段は、上の「1 回あたり」

## 7. 実装の段と、Red から始める spec の見出し

承認のあとの順。段ごとに、Issue を 1 つ、PR を 1 つ。

### 段 1: 選択の検査と、文の組み立て（LLM を呼ばない。gem を足さない）

`spec/lib/nl_query/prompt_spec.rb`

- 候補のカードを、番号つきの 1 行ずつの文にする（ラベル、容器の名前、型、値集合の表示名、単位、テンプレート）
- パス、at-code、説明、`bindings`、`provenance` は、文に現れない
- `bindings` に SNOMED CT のコードを持つカードを渡しても、コードが文に現れない
- 値集合の表示名は、コードが at-code のものだけが文に入る（外の用語のコードの表示名は現れない）
- 同じ入力から、いつも同じ文ができる（並びが決まっている。sha256 が同じ）

`spec/lib/nl_query/selection_parser_spec.rb`

- 番号と演算子と値から、クエリビルダーの選択（カード、演算子、値）を作る
- 値集合の条件は、表示名からコードをカードで引く（「疑い」→ at0074）。LLM がコードを書いても、使わない
- 候補に無い番号は、はねる（理由を返す）
- カードの型に合わない演算子は、はねる
- 値集合に無い表示名は、はねる
- JSON として読めない応答、決まった形でない応答は、はねる（例外を外に出さない）
- 「答えられない」（選択が空で、理由がある）を、そのまま返す

`spec/lib/nl_query/explanation_spec.rb`

- 選択とカードから、説明の文を組む（表示する項目、条件、アーキタイプ、テンプレート）
- 値集合の条件は、表示名とコードの両方を書く
- 説明の文に、記録の中身は現れない

### 段 2: 口と、記録した応答のアダプタ、問い合わせの流れ（gem を足さない）

`spec/lib/llm/adapters/recorded_spec.rb`

- 記録のファイルから、送った文（指示文と入力）の sha256 が同じ応答を返す
- 記録に無い文には、「記録が無い」で落ちる（黙って外を呼ばない）

`spec/lib/llm/settings_spec.rb`、`spec/lib/llm/usage_spec.rb`（10 節）

- 設定が無ければオフ。鍵だけがあってもオフ
- オンの設定があっても、アダプタが使えない（鍵が無い、知らない名前）ときは、外を呼ばない。理由が付く。理由に鍵の値は出ない
- 回数とトークンの数を、日ごとに数える。上限に達したら、呼ばない

`spec/lib/nl_query/runner_spec.rb`

- 問い → 検索 → アダプタ → 選択 → AQL → リンタ → 実行 → 説明、が 1 本でつながる（a002 の問い。記録した応答で）
- オフのとき、候補のカードだけを返す（クエリビルダーに落ちる）
- 回数の上限に達しているとき、アダプタを呼ばず、候補のカードだけを返す。理由が付く
- 応答が読めないとき、候補のカードだけを返す。理由が付く
- リンタの error がある AQL は、実行しない
- アダプタが例外で落ちたとき（通信の失敗、時間切れ）も、候補のカードだけを返す

### 段 3: 画面（gem を足さない）

`spec/requests/queries_nl_spec.rb`、`spec/system/demo_nl_query_spec.rb`

- オフのとき: オフであることと、オンにする方法への案内が出る。問いを文で入れる欄は出ない。クエリビルダーは、これまでどおり動く
- オンのとき: 「問いを文で入れる」欄があり、オンであること、問いの文が外に送られること、費用がかかること、きょう使った回数と上限が出る
- オンのままでも、手で選ぶ欄（探したい項目）は、同じ画面にある
- 記録した応答のアダプタで、問いを入れると、表示する項目と条件が入った状態になる（実行はまだ）
- 実行すると、結果と説明が出る
- 外に送らないアダプタ（記録した応答、手元のモデル）のときは、「外に送られます」の注意を出さない
- 文言は `docs/demo/ui-vocabulary.md` に足し、同じコミットで spec を合わせる
- 口（段 3 で決めた）: `POST /queries/ask`（`nl` に問い）。LLM を呼ぶので GET にしない（読み込み直しで、もう一度呼ばない）。
  選択ができたら、選択を URL のパラメータに直して `GET /queries/new` に移る（303）。作れなかったら、理由と候補のカードを出す（422）
- 利用者むけの説明は `docs/nl-query.md`（オンにする方法、費用、外に送るもの）

### 段 4: API のアダプタ（**gem を足す。人間がマージ**）

`spec/lib/nl_query/adapters/anthropic_spec.rb`

- 鍵が無いとき、「設定されていない」を返す（例外にしない）
- SDK のクライアントの代わりに、同じ口を持つ偽物を差し込んで: 指示文、カードの文、問いが、決まった場所に入る
- 応答の本文から、選択の JSON を取り出す。断り（refusal）は「答えられない」にする
- 通信の失敗、時間切れ、回数の制限は、「答えられない（理由つき）」にする
- 記録に、鍵とヘッダが入らない

SDK の呼び方（クラス、引数、出力の形の縛り方）は、この段の最初に、公式の文書と gem のソースを引用して確かめる（No API guessing）。
実際の API を呼ぶ確かめは、CI に入れず、開発機で人間が鍵を渡したときに 1 回だけ行い、応答を記録して段 2 の記録に足す。

### 段 5: 手元のアダプタ（開発機の設定の変更を含む。ゲート報告）

- 候補のモデルと道具を調べて報告 → 承認 → `spec/lib/nl_query/adapters/local_spec.rb`（偽の HTTP の口で、段 4 と同じ見出し）

### 段 6: 測定

`spec/lib/evaluation/grounding_run_spec.rb`、`spec/lib/tasks/evaluation_grounding_spec.rb`

- 腕（N0、N1、G-AQL、G-選択）ごとに、送る文が決まる（N にカードの文が入らない、G-選択にパスが入らない）
- 記録した応答で、問い × 腕 × くり返しを回し、試行ごとの採点（行の一致、リンタ、実行、カードの一致、読めた）を出す
- 問いごとの「何回のうち何回」と、全体の 3 つの数字（5.4）を出す

`rake evaluation:grounding`（案）は、アダプタと回数を引数で取り、既定では記録した応答だけを使う。外を呼ぶのは、明示したときだけ。

### LLM の応答を固定して試す方法（まとめ）

- spec と CI は、いつも `Recorded`（記録した応答）か、spec の中の偽のアダプタを使う。外を呼ばない
- 記録は、送った文の sha256 を鍵にした JSON のファイル（置き場所の案: `spec/fixtures/nl_query/recordings/`）。
  指示文やカードの文を変えると、sha256 が変わり、記録に当たらなくなる。**黙って古い応答を使わない**ための作り
- 記録の中身は、サンプルデータの問いと、モデルの応答だけ。鍵、ヘッダ、記録の中身（患者のデータ）は入らない
- 記録を取り直すのは、開発機で、人間が鍵を渡したとき。取り直した記録は、差分をレビューできる形（1 問 1 ファイル）で commit する

## 10. オンとオフ、回数の上限（R-20261127-14 で足した節）

### 10.1 設定（環境変数）

| 環境変数 | 意味 | 既定 |
|---|---|---|
| `ANLAGE_LLM` | 使うアダプタの名前（`anthropic`、`local`、`recorded`）。これがオンの設定 | 無し（オフ） |

### 10.2 画面に出すもの

- オン: オンであること、アダプタの名前、きょう使った回数と上限、使ったトークンの数。外に送るアダプタのときは、
  問いの文が外に送られること、費用がかかること、患者の情報を書かないこと
- オンのままでも、利用者は、その都度、文で問うか、手で選ぶかを選べる（同じ画面に両方の欄がある）

### 10.3 回数の数え方（費用の歯止め）

認証が無いので、オンにした Anlage に届く人は、だれでも API を呼べる。回数の上限で歯止めをかける。

- 数えるもの: アダプタを呼んだ回数（成功も失敗も 1 回）、入力と出力のトークンの数（アダプタが返したとき）
- 単位は 1 日（アプリの時刻の日付）。上限は `ANLAGE_LLM_DAILY_CALL_LIMIT`。**上限に達したら、アダプタを呼ばず、クエリビルダーに落ちる**
- 置き場所: **ファイル**（`storage/llm_usage.json`。日付 → 回数とトークンの数）。書くときにファイルをロックする

置き場所の案を比べた。

| 案 | 長所 | 短所 |
|---|---|---|
| **ファイル（採る）** | 表を足さない（migration が無い）。起動し直しても残る。同じ機械の複数のプロセスで合う | 複数の機械に分けた配置では合わない。`storage/` を残さない配置（Docker で volume を付けない）では、作り直しで消える |
| プロセスの中の変数 | いちばん軽い | 起動し直すと 0 に戻る。プロセスごとに別に数える。歯止めにならない |
| DB の表 | どの配置でも合う。履歴を問い合わせられる | migration が要る（ゲート） |

- 実測: `.gitignore` は `/storage/*` を外している。記録のファイルは、リポジトリに入らない
- 表にするかどうかは、段 4 で実際の API を呼ぶ前に、もう一度見る。複数の機械に分ける配置を README が勧めるようになったら、表にする（そのときゲート）
- 既定の 100 回は、Sonnet 5.5 の見込みの値段（6.3 節。1 回 0.026 ドル）で 1 日 2.6 ドルほど。値段は見込みで、段 4 の前に確かめ直す
- 1 日の単位にしたのは、上限に達したあと、手で戻す操作を要らなくするため（次の日に 0 から数える）

### 10.4 README と Docker の手順

- オンにする方法（環境変数の名前）と、費用がかかること、回数の上限を書く。鍵の値は例にも書かない
- 書くのは、外を呼ぶアダプタが入る段 4。段 3 では、画面の案内と、この計画書だけ

## 11. OpenAI のアダプタ（R-20261127-25 で足した節）

生成 AI の API は、Anthropic だけでなく、OpenAI も使えるようにする。決まりは、Claude API のアダプタと同じ（送るもの、鍵の扱い、回数の上限、画面の表示）。
送る文を組むところ（`NlQuery::Prompt`）は共通で、アダプタは、文を送って文を受け取るだけ。

### 11.1 設定

| 環境変数 | 意味 | 既定 |
|---|---|---|
| `ANLAGE_LLM=openai` | OpenAI のアダプタを使う。**どちらの会社に文が送られるかは、`ANLAGE_LLM` で決まる** | — |
| `ANLAGE_LLM_MODEL` | モデルの ID。既定は置かない | 無し |
| `OPENAI_API_KEY` | OpenAI の鍵 | 無し |
| `ANLAGE_LLM_BASE_URL` | 接続先。同じ形の口を持つ、手元のサーバーにも向けられる | `https://api.openai.com/v1` |

- 3 つ（`ANLAGE_LLM=openai`、`ANLAGE_LLM_MODEL`、`OPENAI_API_KEY`）がそろったときだけオン。鍵を置いただけでは、オンにならない。
  `ANLAGE_LLM=openai` のとき、Anthropic の鍵は読まない（逆も同じ）
- 接続先が開発機の中（127.0.0.1、localhost、::1）のときだけ、「外に送らない」扱いにして、鍵が無くてもよい。
  それ以外の接続先は、外に送る扱いで、https だけを受ける（鍵と問いの文を、平文で送らない）

### 11.2 作り方: 公式の SDK を使う案と、標準の HTTP で呼ぶ案

公式の SDK は、ある（gem `openai`。RubyGems の作者は OpenAI、ソースは github.com/openai/openai-ruby。2026-11-27 の最新は 1.3.0。
`OpenAI::Client.new(api_key:)`、`openai.chat.completions.create(messages:, model:)`、`base_url:` も渡せる。README による）。

| | 公式の SDK（gem `openai`） | **標準の HTTP（`Net::HTTP`）。採る** |
|---|---|---|
| 足す gem | 1 つと、その依存 | 無い |
| `Gemfile` を変える PR | 要る（人間がマージ） | 要らない |
| 保守 | 口が変わったとき、gem を上げれば追随できる。型つきの応答、やり直し、時間切れの扱いが付く | 使うのは 1 つの口（Chat Completions）の、数個の項目。口が変わったら、自分で直す |
| 鍵と例外 | SDK の例外の文は、URL や本文を含みうる。Claude API のアダプタと同じく、文を使わず、状態の番号で理由を作る | 例外は標準のもの（時間切れ、接続の失敗）。応答の本文は、理由に使わない。鍵は、ヘッダに入れるだけ |
| 手元のサーバー | `base_url:` で向けられる | 接続先を変えるだけ。同じアダプタで、同じ形の口を持つ手元のサーバーにも届く（段 5 の材料） |

**標準の HTTP を採る**。理由: 使う口が 1 つで小さい（60 行ほど）。gem を足さないので、置けば動く、を保ちやすい。
Chat Completions の形は、ほかの道具（手元のサーバー）も真似ている形で、接続先を変えるだけで使い回せる。
捨てたもの: SDK のやり直しと型。やり直しは、しない（画面の 1 回の問い合わせ。落ちたら、手で選ぶ欄に落ちる）。

- 使う口は Chat Completions（`POST /v1/chat/completions`）。公式の文書は、新しく作るものには Responses の口を勧めている。
  Chat Completions を採るのは、手元のサーバーが真似ているのが、この形だから。Responses に替えるかは、段 5 のあとで見直す
- Claude API のアダプタは、公式の SDK のまま（PR #235）。2 つのアダプタで作りが違うが、どちらも `Llm::Adapter` の口の中に閉じる

### 11.3 口の形（公式の文書で確かめた。2026-11-27）

- 要求: `POST <接続先>/chat/completions`、ヘッダ `Authorization: Bearer <鍵>`。本文は `model`、`messages`（`role` は `system` と `user`）、
  `max_completion_tokens`（`max_tokens` は deprecated）
- 応答: `choices[0].message.content`（文字か null）、`choices[0].message.refusal`、`choices[0].finish_reason`
  （`stop`／`length`／`content_filter`／`tool_calls`）、`model`、`usage.prompt_tokens`・`completion_tokens`
- 状態: 401（鍵の誤り）、429（回数の制限）、500・503。**エラーの本文の形は、読んだページには書かれていなかった**。本文は読まず、状態の番号だけを使う
- 文書は、新しいモデルでは、指示には `developer` の役を使う、と書く。`system` も受ける、と読める。**実際のモデルで `system` が通るかは、
  鍵が渡ったときに確かめる**（通らなければ `developer` に替える。手元のサーバーが `developer` を知っているかも、段 5 で見る）
- 出力の形を縛る機能（`response_format` の `json_schema`）は、Claude API のアダプタと同じ理由で、まだ使わない

### 11.4 モデルの ID と値段（公式の文書。2026-11-27。100 万トークンあたり、入力／出力）

| モデルの ID | 値段 | 公式の文書の説明 |
|---|---|---|
| `gpt-6.2-astra` | 8 ドル／40 ドル | 上位 |
| `gpt-6.2-sol` | 2 ドル／10 ドル | ふだん使い |
| `gpt-6.1-terra` | 1 ドル／5 ドル | — |

### 11.5 測定の腕に足す案（足すかどうかは、鍵が渡るときに人間が決める）

- 案: Claude の 2 つ（Sonnet 5.5、Haiku 5.5）に、値段の帯が同じ OpenAI の 2 つ（`gpt-6.2-sol`、`gpt-6-luna`）を足す。
  同じ問い・同じ指示文・同じカードの文で、モデルだけを替える（3.3 節の比べ方のまま）。出どころが 2 社になり、「1 社のモデルでしか測っていない」という限界が弱まる
- 費用の見込み（6.3 節と同じ置き方: 1 回が入力 3,000・出力 2,000 トークン、600 回。**見込み。トークンの数は、まだ測っていない**）:
  `gpt-6.2-sol` は 16 ドルほど、`gpt-6-luna` は 0.8 ドルほど。Claude の 2 つ（17 ドルほど）と合わせて **34 ドルほど**
- 上限は、合わせて 50 ドルのまま。34 ドルの見込みに、指示文の調整とやり直しを足すと、余りは小さい。
  最初にトークンの数を測り、超えそうなら、回す前に報告する（安いほうの 2 つだけで測る、回数を減らす、などの案を付ける）

## 13. 並べ替え（R-20261127-26 の 5 で足した節。`skoba/anlage#242`）

クエリビルダーに、並べ替え（どの項目で、昇順か降順か）を足す。8 節の「入れないもの」から、並べ替えを外す（集計と、2 つ以上のアーキタイプの結合は、入れないまま）。

### 13.1 形

| 層 | 足すもの |
|---|---|
| `QueryBuilder::Builder` | `order: { card:, direction: :asc／:desc }` → `ORDER BY <パス> ASC／DESC` を、WHERE のあとに足す。数値は `…/magnitude`、文字列（値集合を含む）は `…/value` |
| `QueryBuilder::Linter` | `ORDER BY` のパスも、SELECT・WHERE と同じ検査に通す |
| `QueryBuilder::Runner` | `order:` を受けて、ビルダーに渡す |
| 画面 | 「並べ替え」（並べ替えない／表示する項目）と、向き（昇順／降順）。URL のパラメータは `order`（項目の参照）と `order_direction`（`asc`／`desc`） |
| 文で問う | 選択の JSON に `"order": {"card": 番号, "direction": "asc" か "desc"}`（無ければ null）。検査、画面への受け渡し、説明の文（「『発症日時』の昇順に並べます。」）が追随する |

- 並べ替えの項目は 1 つ。2 つ以上の項目での並べ替えは、入れない
- 並べ替える項目は、表示する項目と同じ ENTRY のアーキタイプのもの（1 本の AQL で使えるのは 1 つ）。表示しない項目でも並べ替えに使える
  （画面で選べるのは、表示する項目。文で問うの選択は、候補のどの項目でも指せる）
- 実測（openehr 2.6.1 のソース）: 文法は `ORDER BY 識別パス (ASC|DESC)?` を並べたもの（`lib/openehr/aql/parser.rb:414-430`）。
  実行は CONTAINS → WHERE → ORDER BY → SELECT の順で、値の無い行は、向きによらず最後に来る（`lib/openehr/aql/engine.rb:10・46-70`）

### 13.2 まだ組まないもの

| 何 | 理由 | いつ |
|---|---|---|
| **日時の項目での並べ替え** | 日時そのものの順で並べる（R-20261127-26）。openehr 2.6.1 では、日時そのものの順が月末で逆になることがある（既知の制限 20）。値の文字（`…/value`）で並べれば 2.6.1 でも正しいが、それは時刻帯の書き方がそろっているときだけで、日時そのものの順ではない | 直った openehr の版が main に入ってから、spec を確定して使えるようにする。それまでは「日時の項目での並べ替えは、まだ使えない」で、実行しない |
| 版をまたいで引くときの並べ替え | 版ごとの AQL を別々に実行して、行をつなぐ。AQL の `ORDER BY` は、版ごとの中の順にしかならない | アプリの側で、つないだ行を並べ直す形を、要るようになったら足す |

### 13.3 測定とのかかわり

- n013-2（「…発症日の順番に並べてください」）は、発症日時（日時の項目）での並べ替え。**いまは組めない**ので、行の順を見ない採点のままにする。
  日時の並べ替えが入ったら、n013-2 の採点で行の順を見る
- 指示文（`NlQuery::Prompt::INSTRUCTIONS`）に `order` の説明が増えたので、送る文の sha256 が変わる。モデルの応答の記録は、まだ 1 つも無い（影響なし）
- 接地なしの腕と AQL を書かせる腕は、AQL に `ORDER BY` を自分で書ける。方言の説明に、日時の項目では使えないことを書く
