# S3（検索の強化）の計画

裁定 ID: R-20261124-21（作業列 4）。状態: **ゲート報告（6 節の問いへの回答待ち）**。実装は公開 v0.2.0 のあと。

- 基準点: anlage main `66f3a85`（openehr 2.5.0、openehr-rails 0.9.0）
- 対象: パスカード検索 `Opt::PathcardSearch`（`app/lib/opt/pathcard_search.rb`）。問い（日本語）→ カードの順位つきの列
- 測り方: 評価 v2（`docs/design/s1-eval-v2-plan.md`、`rake evaluation:run`）の before／after
- 入力: 評価 v2 で見えた 2 点（c015「臨床検査」、c008「発症」）と、v1 の完全失敗 2 問（q16「BMI」、q18「既往」）
- 関連 Issue: `skoba/anlage#122`（同点の順序が登録順で決まる）

## 1. いまの検索（実測）

`app/lib/opt/pathcard_search.rb` は、問いとカードをそれぞれ文字の bigram の集合にし、共通の bigram の数を score にする。

- カード側の文は、ラベル・説明・値集合の表示（`code_list[].label`）・祖先の名前（`container_labels`）をひとまとめにしたもの。項目ごとの重みは無い
- score が 0 のカードは出ない。並びは score の降順だけで、**同点のときの順序を決めていない**（`sort_by`。入力の順＝テンプレートの登録順とカードの並びがそのまま残る）
- 索引は active の版のテンプレートのカード

## 2. 評価 v2 で見えた 2 点の原因（実測）

### 2.1 c015「臨床検査」: 索引によって負例が 1 位に出る

問いの bigram は「臨床」「床検」「検査」。当たるカードは 4 枚で、**4 枚とも score 1**（同点）。

| カード | 当たった bigram | 当たった項目 |
|---|---|---|
| ProblemList at0003「臨床的に認識された日時」（負例） | 臨床 | ラベル |
| LabResultReport laboratory_test_result at0005「検査名」 | 検査 | ラベル、祖先の名前 |
| LabResultReport laboratory_test_analyte at0024「分析名」 | 検査 | 祖先の名前 |
| LabResultReport laboratory_test_analyte at0001「分析結果」 | 検査 | 祖先の名前 |

同点なので、順序はテンプレートの登録順で決まる。

| 登録順 | 並び |
|---|---|
| bmi_calculation → ProblemList → CardiologyEncounter → LabResultReport（spec の 4 テンプレート） | at0003（負例）→ at0005 → at0024 → at0001 |
| LabResultReport → bmi_calculation → CardiologyEncounter → ProblemList（同じ 4 つを別の順で） | at0005 → at0024 → at0001 → at0003 |
| `rake demo:reset` の 5 テンプレート（CardiologyEncounter、LabResultReport、ProblemList、…） | at0005 → at0024 → at0001 → at0003 |

- **原因はテンプレートの数ではなく、登録の順序**。`docs/reports/s1-eval-v2-log.md` R15 に書いた推論（「bigram の重みがコーパスの文書数で変わる」）は誤りで、
  重みはどこにも無い。4 つを別の順で登録すると、5 テンプレートのときと同じ並びになる（上の表の 2 行目）
- 5 テンプレートで負例違反が出ないのは、at0003 がたまたま 4 位（top-3 の外）に落ちるから。同点であることは変わらない

### 2.2 c008「発症」: 第 2 候補（プロブレム・診断名 at0002）が結果に出ない

問いの bigram は「発症」の 1 つ。当たるのは at0077「発症日時」（ラベル）の 1 枚だけ。

- at0002「プロブレム・診断名」の文（ラベル、説明、祖先の名前「プロブレム・診断」）に「発症」は無い。字面では届かない
- at0002 が第 2 候補になるのは、臨床の文脈（「発症した病名」）による。字面の重なりではなく、**同じ ENTRY の中の主要な項目**という構造か、言い換えの知識が要る

### 2.3 v1 の完全失敗 2 問（参考。評価 v2 でも同じ）

- q16「BMI」→ body_mass_index: カードの文は日本語（「体格指数」）で、英字の略語が無い。別名が要る
- q18「既往」→ problem_diagnosis: 記録の語彙（プロブレム・診断）と、問いの語彙（既往）が違う。別名か意味の近さが要る

## 3. 直す順（案）

段ごとに評価 v2 の before／after を取り、効かなかった段は入れない。

| 段 | 中身 | ねらう問い | 要るもの |
|---|---|---|---|
| A | **順序を決定的にする**: 同点のときの順序を、登録順でなくカードの内容で決める（score → 当たった項目の強さ → template_id・path）。#122 | c015 の結果が索引の作り方で変わらない | コードだけ |
| B | **項目の重み**: ラベル ＞ 祖先の名前（近い祖先ほど重い）＞ 値集合の表示 ＞ 説明。当たった bigram の数ではなく、問いのうち何割を覆ったかも見る | c015、q07（at_code まで見ると 2 位） | コードだけ。重みの値は評価 v2 で決める |
| C | **同じ ENTRY の主要な項目を第 2 候補に出す**: 当たったカードと同じアーキタイプのルートを持つカードを、低い score で後ろに足す | c008 の第 2 候補 | コードだけ。何を「主要」とするかはカードから取る（6 節の問い 3） |
| D | **別名表**: 問いの語 → カードの語（略語、記録語彙と節名、一字違い）。人間がレビューした表を読む | q16、q18、c015 | 表の出どころ（6 節の問い 1） |
| E | **埋め込みとのハイブリッド**: カードの文と問いをベクトルにして、bigram の score と合わせる | q18、c008、言い換え全般 | モデル、gem、格納先（6 節の問い 2） |

- A と B は外に何も足さない。先に入れて、どこまで届くかを見る
- B だけでは c015 の負例は消えない見込み（推論）: at0003 はラベルに当たっていて、祖先の名前だけに当たる 2 枚（分析名・分析結果）より強くなる。
  「臨床検査」の中心が「検査」にあることは、字面からは決まらない。D か E が要るかを、B のあとの実測で決める
- C は、検索の結果に「当たっていないカード」を足すので、画面での見せ方（なぜ出たか）も決める

## 4. 評価

- 指標は評価 v2 のまま（Top-1、Top-3、MRR、recall@3、負例違反、順位遵守）。段ごとに `docs/reports/` のログに before／after を貼る
- **索引の作り方を名前で固定する**: card の問いも、aql の問いの `dataset` と同じように、名前つきの索引（例: `demo_initial`、4 テンプレート）の上で採点する。
  いまは「そのとき DB にあるカード」で採点していて、c015 のように結果が索引の作り方で変わる
- 段 A のあと、同じカードの集合なら登録順を変えても同じ並びになることを spec で固定する（#122 の acceptance criteria）
- 問いが 21 問（v1 の 17 ＋ v2 の card 4）と少ない。段 D・E の評価には足りない見込みなので、問いを足す案を段 B のあとに出す（臨床のレビューは人間）

## 5. 守ること

- LLM 分業原理: 別名表と埋め込みが供給するのは「問いの語とカードの対応付け」だけ。カードの意味・パス・制約は OPT から取ったものを変えない
- コンテンツ防火壁: ライセンスのある用語マスターの中身を、別名表に写さない・埋め込みにしない・外部 API に送らない。
  埋め込みにするのは、公開アーキタイプ由来のカードの文（ラベル・説明・祖先の名前）と、利用者の問い
- 実物主義: 別名表の語は、評価の注記や様式の欄名など、出どころを示せるものだけ。捏造しない
- 依存の方針: gem の追加は「必ず止まる」。段 E は gem と格納先を決めてからゲート報告

## 6. ゲートで問うこと

1. **別名表（段 D）の出どころとレビュー**: 表を誰が作り、誰がレビューするか。セッションが案を出せるのは、評価 v1・v2 の注記と、
   登録済みテンプレートの節名から拾える対応まで。臨床の言い換え（既往 → プロブレム・診断 など）は人間のレビューが要る
2. **埋め込み（段 E）の実行場所**: 手元で動くモデルか、外部の API か。外部の API なら、カードの文と利用者の問いを外に送ることになる。
   どちらにするかで、gem・格納先（SQLite のまま持つか）・CI の作りが変わる
3. **c008 の第 2 候補（段 C）の考え方**: 「発症」で「プロブレム・診断名」を第 2 候補に出すのを、構造（同じ ENTRY の主要な項目を足す）でやってよいか。
   足す項目の選び方は、臨床の判断を含む（どの項目が主要か）
4. **段 A・B を v0.2.0 の前に入れるか**: 裁定は「S3 の実装は v0.2.0 のあと」。#122（順序が登録順で決まる）は不具合なので、段 A だけ先に入れる選択肢がある
5. **評価の問いを足す時期と数**: 段 D・E の効果を測るのに、いまの 21 問で足りるか

## 7. 範囲外
