# 患者の画面（U1）の計画と見た目の基準

裁定 ID: R-20261127-10 の 3。状態: **承認済み（R-20261127-13。下の「承認と回答」）**。
基準点: anlage main `ae6eb5e`（タグ `v0.2.0` = `dc0402d` のあと。openehr 2.6.1、openehr-rails 0.11.0。PR #211 で 0.12.0 に上げる予定）。

目標（小林、11/27）: Anlage は、すべての EHR の原基。モデルの上に、ロジック、画面と流れ、利用者の層を、どれも定義として持ち、
実行時に置く。まず、患者を開くと、カルテに見えるようにする。

この計画の範囲は、1 節（既定の画面）を実装する U1 と、2 節（画面の定義）・4 節（ロジック）の**書式の案**まで。
認証は入れない（5 節）。

## 承認と回答（R-20261127-13、2026-11-27）

計画は承認された。7 節の問いへの回答:

1. 検査値の系列の鍵は **(a)**。分析名（at0024）の値で系列を分ける。「この field が分析の名前である」ことはテンプレート（アーキタイプ）が
   決めていて、記録が持つのは、どの分析かという値（意味を記録の JSON から作ることには当たらない）
   - 文字列が完全に同じものだけを同じ系列にする。表記のゆれはまとめない
   - 単位が違う記録は、1 つの系列のグラフに混ぜない（扱いは 1.5 節）
   - 既知の制限 21: 分析名が自由記述なので、表記がゆれると系列が分かれる。本来はコード（用語）で分ける
   - **検査の見せ方を改める**（統括の案。臨床のレビューは小林）: 検査は、項目を行、日付を列にした 1 つの表（検査結果の時系列表）を
     基本にする。グラフは、2 点以上ある項目について、表の行から開ける。血圧と、身長・体重・BMI は、1.3 節のとおり（グラフと表）
2. 外部の CSS の枠組みは足さない
3. グラフはサーバで SVG を描く
4. 式の評価は自前のまま
5. 2 節の書式を、定義の層の計画の出発点にする（定義の層の計画書で、生成 AI が書きやすく検査できる形に直す）

## 1. 既定の画面（定義が無くても立ち上がる）

### 1.1 材料

| 材料 | 出どころ | 使い方 |
|---|---|---|
| 記録 | RM グラフ `OpenehrRails::Rm::Composition.latest.not_deleted.where(ehr:)`（患者の画面の一覧と同じ） | 患者の記録の集合 |
| 値 | `Opt::CompositionReader`（記録の中身 #191 と同じ。読み戻せない記録は値を取らない） | 部品に入れる値 |
| 意味 | 登録済みのテンプレートの `web_template`（field の label・rm_type・units・code_labels・input_kind、entry の rm_type・archetype_id、`Opt::FormLayout` の入れ子） | 部品の見出し、列名、単位、選択肢の表示、並び |
| 時刻 | OBSERVATION のイベント時刻（読み戻した値の時刻）、無ければ `context_start_time` | 時系列の横軸、一覧の日付 |

テンプレートが登録されていない記録（初期データの紹介状。12b）は、意味が引けないので、部品に入れず「そのほかの記録」の一覧に出す
（押すと閲覧の画面。#182）。記録の JSON から意味を作らない。

### 1.2 部品を決める規則（RM の型とアーキタイプから）

上から順に当てはめ、最初に当たった規則で決める。

| # | 条件（テンプレートの entry と field） | 部品 | 中身 |
|---|---|---|---|
| R1 | entry の archetype_id が `openEHR-EHR-EVALUATION.problem_diagnosis.v1`（どのテンプレートでも） | **プロブレムリスト** | 1 行 = 1 つの記録の 1 つの entry。列は field の label: 診断名（at0002）、診断確度（at0073、code_labels の表示）、発症日（at0077）。記録日 |
| R2 | 記録の entry に INSTRUCTION がある（テンプレートの entry の rm_type） | **依頼と紹介状** | 1 行 = 1 記録。列: 記録日、テンプレート上の名前、紹介先（INSTRUCTION の protocol の organisation があれば）。押すと記録の画面（「記録の中身」） |
| R3 | entry の rm_type が OBSERVATION で、field の rm_type が DV_QUANTITY または DV_COUNT | **時系列（表とグラフ）** | 系列 = （template_id、field の name）。横軸はイベント時刻、縦軸は値。単位は field の units（記録の単位がほかなら、その記録の単位を表に出し、グラフの系列を分ける）。表は日付 × 系列 |
| R4 | それ以外の記録 | **記録の一覧** | いまの「カルテ記録」の一覧（テンプレート、記録日） |

- R1 を archetype_id で決めるのは、問題・診断の entry の意味（病名・確度・発症日）が、アーキタイプで決まっているから
  （CKM の公開アーキタイプ。at-code は OPT の実物と一致することを spec で確かめる）。R1 の列の at-code の表は、
  OPT から引けない「部品の対応」なので、`config/` の表に置く（下の 2 節の定義の既定値になる）
- R3 の系列の名前は field の label（例: 「収縮期」）。同じ label の field が 2 つのテンプレートにあれば、テンプレート上の名前で区別する
- **問い（ゲート）**: LabResultReport の検査値は、分析名（at0024）が**自由記述の値**で、テンプレートの field は「分析結果」の 1 つだけ。
  R3 のままだと、HbA1c も空腹時血糖も 1 つの系列「分析結果」に混ざる。案:
  - (a) R3 の系列の鍵に、同じ埋め込み CLUSTER の中の DV_TEXT の「名前の field」（at0024）の**値**を足す。系列の名前は記録の値になる
    （意味はテンプレートが「この field は分析名」と言い、名前の文字列は記録が持つ）。どの field を名前に使うかは、2 節の定義の既定値の表に置く
  - (b) LabResultReport は時系列にせず、記録の一覧（R4）に落とす。系列にしたいテンプレートは、2 節の定義で系列の鍵を書く
  - 推す案は (a)。検査値の推移はカルテの中心で、初期データの検査 42 件がすべて LabResultReport。(a) は「記録の値を名前に使う」ので、
    裁定の「意味はテンプレートから。記録の JSON から作らない」に照らして判断を求める

### 1.3 画面の並び（既定）

1. 見出し（患者 ID）と、患者の情報（名前空間、EHR ID、「EHR ID を写す」、「この患者の記録を AQL で引く」〔#211〕、「この患者を選ぶ」）

部品の数が多い患者でも横スクロールを出さない（1280×720。#47 裁定 E）。

### 1.5 検査結果の時系列表（回答 1 で改めた形）

- 行 = 系列（テンプレート、分析名の値〔完全一致〕、単位）。列 = 日付（記録の日付の古い順。同じ日に 2 件あれば、1 つの欄に時刻の順で「／」で並べる。2026-11-27、R-20261127-20 で改めた。列を分けると、見出しに時刻が要るため）
- 単位: 同じ分析名で単位が違う記録は、**単位ごとに別の行**にする（行の見出しは「分析名（単位）」）。換算しない。
  1 つのグラフには 1 つの単位の行だけを描く
- グラフ: 2 点以上ある行に「グラフ」のリンクを付け、押すとその行の折れ線（SVG）を表の下に開く。1 点の行はリンクを出さない
- 並び: テンプレートの登録順、テンプレートの中では、分析名が最初に現れた記録の日付の順
- 血圧（CardiologyEncounter・patient_blood_pressure.v1）と、身長・体重・BMI（bmi_calculation）は、1.2 の R3 のまま（系列ごとのグラフと表）。
  検査結果の時系列表に入るのは、系列の鍵に分析名（名前の field）を使うテンプレート（初期データでは LabResultReport）

## 2. 画面の定義（U2 の入口。書式の案まで）

既定の画面を、定義で上書きできるようにする。定義は YAML。テンプレートと同じく、実行時に置く（ファイルの取り込みで登録し、
データベースに版つきで持つ。登録の表を足すので、実装は migration を伴う〔U2 でゲート〕）。

```yaml
# 画面の定義（案）。id で引き、版を持つ
screen: patient_chart_diabetes
version: 1.0.0
title: 糖尿病の外来
applies_to: patient             # 患者を開いたときの画面
sections:
  - component: problem_list
    from: { archetype: openEHR-EHR-EVALUATION.problem_diagnosis.v1 }
    columns: [ at0002, at0073, at0077 ]
  - component: time_series
    from: { template: LabResultReport, field: laboratory_test_analyte_at0001 }
    series_key: laboratory_test_analyte_at0024   # 1.2 の問いの (a) の既定値を、定義で書く形
    only: [ HbA1c, 空腹時血糖 ]
    chart: line
  - component: time_series
    from: { template: CardiologyEncounter, fields: [ blood_pressure_at0004, blood_pressure_at0005 ] }
    chart: line
  - component: records
    from: { rm_type: INSTRUCTION }
  - component: buttons
    items:
      - label: 検査結果を入力
        open: { form: LabResultReport, then: { screen: patient_chart_diabetes } }   # 入力が終わったあとに進む画面
      - label: 紹介状を書く
        open: { form: jp_referral, then: { record: saved } }                         # 保存した記録の画面へ
```

- 部品は 5 つ: `form`（帳票）、`records`（記録の一覧）、`table`、`time_series`（表とグラフ）、`buttons`。既定の画面（1 節）は、
  この定義の 1 つの例として書ける形にする（既定の画面 = 組み込みの定義）
- 帳票の入力が終わったあとに進む画面（`then`）と、ボタンで開く画面（`open`）を指定できる（小林。Better の EHR Studio で確かめた使い勝手）
- 参照は template_id・field の name・archetype_id・at-code（いずれもテンプレートから引けるもの）。登録のときに、参照がテンプレートに実在するかを
  検査する（クエリビルダーのリンタと同じ考え方。無い参照は登録できない）
- この計画では書式の案まで。U2 の計画で、登録の表、版、検査、画面の選び方（患者ごと・利用者ごと）を決める

## 3. 見た目の基準（シンプルで、整える）

### 3.1 基準（1 枚。`docs/design/visual-guidelines.md` に分けて書く。U1 の最初の段）

| 項目 | 基準 |
|---|---|
| 色 | CSS 変数で定義する（`--color-text`、`--color-muted`、`--color-border`、`--color-surface`、`--color-accent`、`--color-danger`、`--color-warning`）。いまの値（`#ccc`、`#f3f4f6`、`#b91c1c`、`#1d4ed8` など）を変数にまとめ直す。明るい配色だけ（暗い配色は範囲の外） |

### 3.2 外部の枠組みを足すか

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| **足さない（推す）** | `application.css` を、変数・部品ごとのファイル（Propshaft が束ねる）に分ける | 依存が増えない。画面の定義（2 節）の部品と CSS の部品が 1 対 1 になる。いまの 158 行から積める | 部品を自分で書く量は増える |
| Tailwind（`tailwindcss-rails`） | クラスで書く | 早く整う | gem とビルドの段が増える（Docker のイメージも）。実行時に置く画面の定義から、クラス名を組むことになる |
| Pico.css など（CDN または vendor） | 要素に既定の見た目 | 1 ファイルで整う | 見た目の決定を外に預ける。表と帳票の細部は結局上書きする |

推すのは「足さない」。足すならゲート（依存の方針）。

### 3.3 グラフの描き方

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| **サーバで SVG を描く（推す）** | helper が系列から `<svg>` の折れ線（軸、目盛り、点、単位）を組む。JavaScript は使わない | 依存なし。spec（request と実ブラウザ）で点の数と座標を確かめられる。印刷でも出る | 拡大・ツールチップは無い（表を下に置くので値は読める） |
| Chart.js（importmap で pin） | クライアントで描く | 描画が豊か | JS の依存が増える。値を data 属性で渡すので、spec は実ブラウザでしか見られない |

推すのは SVG。足すならゲート。

## 4. ロジックを置く（U3 の入口。1 節だけ）

- いま: `config/form_behaviors.yml`（template_id → rules: target・inputs・formula・cases・round・on・editable）を、アプリの起動時に読む。
  式は `Opt::Formula`（閉じた文法の再帰下降。サーバが権威）と、同じ文法の JS の小評価器（`form_behaviors_controller.js`）
- 案: 振る舞いの定義を、テンプレートと一緒に実行時に登録できるようにする。取り込みの画面で OPT と一緒に（または後から）YAML を置き、
  テンプレートの版に結び付けて持つ。書式は今の rules のまま（template_id は登録先で決まるので書かない）。参照（target・inputs）が
  テンプレートの field に実在するかを登録のときに検査する
- **いまは YAML の軽い定義を優先し、GDL2 が普及した時点で乗り換える**（小林、11/27。R-20261127-16）。GDL2 は openEHR の仕様として正式に
  採用されている（STABLE）。採らない理由は普及の見込み。乗り換えの条件: 主な実装が GDL2 を採用し、定義を持ち運ぶ相手ができたとき。対応の表は定義の層の計画書に書く
- 式の評価に gem を使う案（例: dentaku）と、自前（`Opt::Formula`）のままの案:

| 案 | 良い点 | 弱い点 |
|---|---|---|
| **自前のまま（推す）** | サーバとクライアントで同じ閉じた文法を持てる（即時表示とサーバの権威が食い違わない）。依存なし | 関数を足すたびに 2 か所（Ruby と JS）を直す |
| dentaku（Ruby の式の gem） | 関数が多い | クライアント側に同じ評価器が無い（JS で別の評価器を持つと、文法が食い違う）。gem の追加はゲート |
